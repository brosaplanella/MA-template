Sources (all read-only; nothing in reference/ was modified, built or rendered):

Categories:

  • Generic: goes into the template.
  • Module: specific to MA147 and stays behind.
  • Content: lecture material; the template gets a small placeholder that shows the same pattern.

1. Summary

  1. There are three separate Quarto projects with two separate design lineages.
    • The notes are a book: scrbook, Bootswatch flatly/darkly, KaTeX, blue links, no shared filter.
    • The sheets (assignments + problem sheets) are articles: fancyhdr running header, sans-serif headings, an aubergine accent colour, the default HTML math engine (MathJax), a Lua filter, self-contained HTML.
    • The two sheet projects are near-copies of each other, kept in sync by hand (“If you change the macros or styling in one project, copy the file to the other”), and they have already drifted: difficulty icons exist only in the problem sheets.
  2. The sheets are the more generalised half. Their _shared/ folder is close to what the template needs:
    • one macro file injected into both PDF and HTML;
    • a filter for marks, marker notes and centred/info boxes;
    • a hide-marking switch;
    • a mark-total checker;
    • a “CONFIDENTIAL” banner driven by a solutions: true flag;
    • module/term metadata set once in _quarto.yml.
    The notes have none of this. Their macros.qmd (99 macros from another module) is entirely unused.
  3. There is still no release mechanism, but there are the building blocks for one.
    • Assignment solutions are separate files with solutions: true, which adds the banner.
    • hide-marking: true strips the marks and marker notes.
    Together these are almost exactly the “student build of a released solution”: turn off the confidential banner, strip the marking, add a “released on” banner. What is missing is the per-assignment flag, the student/staff split of the outputs, and the leak check. Right now _output/assignment-1/ holds assignment-1.pdf and assignment-1-solutions.pdf side by side, so the brief’s main risk (“distributing the wrong build”) is live today.
  4. The three projects are coupled through the author’s local folder layout. Two assignment solutions do sys.path.insert(0, "../../Lecture notes") to import utils.py. Sheets refer to “Example 4.4”, “Example 2.13”, “Algorithm 2.1” of the notes by hard-coded number. Both break silently when the notes move or are renumbered. This is a strong argument for one repo holding all three types.

5. Things that quietly assume first-year maths (or MA147)

  • Notes:
    • the “boxed = examinable” promise;
    • A-Level references;
    • “Week 6 breathing week”;
    • module URLs with the year in them;
    • hand-typed notation;
    • usetex=True.
  • Assignment rubric: “two of three questions marked, out of 20, plus 5 for clarity”, hard-coded in a shared header. Other modules (and MA302) will differ, so it needs to come from settings.
  • Submission text: “upload via Moodle … single PDF … typed or scanned”. This is Warwick-specific; make it a setting with this as the default.
  • Deadlines: free text with Warwick week numbers (“Thursday (week 2), 12 noon (UK time)”). Fine to display, but it should be data (a date plus an optional label), so release dates and checks can use it.
  • Question shape: ## Question N with (a), (b) parts. This assumes short-answer calculus-style questions; it’s fine for most maths. Sheets have no theorem/proof environments; a proof-heavy (pure) module would want .proof and theorem blocks in sheets too.
  • Difficulty icons are springs: a mechanics joke that suits MA147/MA302. Make the glyph configurable (default: stars or plain numbers).
  • Figure style: serif + Computer Modern mathtext in the sheets versus sans in the notes. Neither is wrong, but the two document types will look different side by side.
  • Python everywhere: every sheet that plots needs jupyter: python3 (it’s a default project, so there is no auto-detection). A module with no figures should need no Python.
  • “Solutions” in the title: the running header strips -- Solutions / – Solutions from titles with a regex. This assumes English titles and that exact convention.

6. Beyond the three types (“and even more”)

The same infrastructure (macros, filter, palette, figure style, banners, release flags) covers these with little extra work. Listed only so the design leaves room for them, not for v0.1:

  • Worksheets / class handouts: like problem sheets, possibly with gaps to fill in.
  • Formula sheet / cheat sheet: single page, no solutions.
  • Computer labs / companion notebooks (coffee_cup.ipynb): .ipynb or .qmd rendered to HTML.
  • Mock / practice exams: sheet-type with marks (same filter as assignments), but real exams stay out per the brief, so a “mock” type must not become a back door.
  • Slides: the brief puts PowerPoints outside, but Quarto revealjs/beamer would reuse the macros and palette if you ever want them.

A useful way to frame it: there are two layouts (book, sheet), one shared style layer, and per-type switches (marks, marker notes, difficulty, header box, solutions audience). A new type should be “a new switch combination”, not a new copy of _shared/.

7. Risks, surprises and questions

Risks

  1. Wrong build distributed: this is live today. _output/assignment-N/ mixes assignment-N.pdf and assignment-N-solutions.pdf (with self-contained HTML of both). Uploading a folder, or picking the wrong file, sends the marker solutions. The banner helps, but the filenames don’t differ enough (-solutions is what the brief reserves for released student solutions, so the staff ones need -STAFF).
  2. The sheets have no version control. Neither sheet folder is a git repo (there’s no .git in either; they’re only visible as ignored paths of MA-template). If that’s true for your real copies too, the only history of the assignment solutions is OneDrive.
  3. Copy-and-sync drift. The two _shared/ folders have already diverged. A third copy for notes, and a fourth for MA302, would make this worse. The template should make sharing structural (one repo, or one shared folder), not manual.
  4. Breakable coupling: the ../../Lecture notes path hack and hard-coded “Example 4.4” references. Folder names with spaces (“Lecture notes”, “Problem sheets”, “Old assignments”) also invite quoting bugs in scripts and CI on all three OSes.
  5. Public notes vs. private solutions. You confirmed the MA147 GitHub repo is the lecture notes only, and it is public and linked to students. The brief wants the template repo private because it holds assignment solutions. Putting all three types in one repo (good for consistency) means the notes source stops being public. See Q1.
  6. Carried over from the first pass:
    • The notes CI likely can’t pass on Linux (no Python step; figs\\… paths).
    • freeze + cache won’t notice changes to utils.py.
    • MA147’s git history still contains MA302 files, including a file named figs/short_term_academic_leave_form.pdf. You said the repo is just lecture notes; it may be worth a one-minute check that this file is a blank form, since the history is public.

Surprises

  • The sheets already solve the problem the brief calls “macros in both formats”. The notes should adopt the sheets’ approach, not the other way round.
  • hide-marking already turns an assignment solution into a student-safe document. The release feature is maybe 70% there.
  • Students never see per-question marks in the assignment sheets; marks live only in the solutions.
  • Problem-sheet solutions are student-facing but currently have no “released” notion at all. Are they released with the sheet, or a week later?

Questions for you

  1. One repo or several? I’d recommend one private repo per module containing notes, problem sheets and assignments (shared settings, macros, filter, utils; real cross-references). The cost is that the notes source is no longer public; students get the built notes via Moodle as now. Is that acceptable, or must the notes source stay public (which means two repos: public notes + private sheets, sharing a template)?
  2. Problem-sheet solutions: do they need release control too (released per sheet, like assignments), or are they always public once written? Do they ever contain anything staff-only?
  3. Settings format: is it OK to move deadline and release_date into _module.yml as a per-assignment list (date + optional “week N” label), so the sheet header, the release flag and the leak check all read the same entry?
  4. Old LaTeX folders: should they go in the repo (e.g. an archive/ folder outside the render scope), or stay in OneDrive with the exams?
  5. One look or two? Should the notes adopt the sheets’ visual identity (accent colour, sans headings, serif figures), should the sheets adopt the notes’, or should each keep its layout but share palette, macros and figure style?
  6. Cross-references to the notes from sheets (“Example 4.4”): worth solving in v0.1 (only feasible in a single repo, e.g. via a generated label→number map), or park it and keep hand-typed numbers?
  7. Macro names: adopt the sheets’ set (\mbR, \dv, \dd, \eps; they also match your old LaTeX), drop the notes’ unused macros.qmd, and leave the notes’ hand-typed \mathrm{d} as is (converting it would be a content change)?
  8. Math engine: standardise on MathJax (the sheets’ current default, more LaTeX-compatible) or KaTeX (the notes, faster)?
  9. Difficulty glyph: keep springs as the default, or make the template neutral (stars or numbers) with springs as MA147’s override?
  10. Are there other document types you already produce, or plan to, that should be in the first design (worksheets, formula sheet, labs, mock exams)?
